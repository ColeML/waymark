# Waymark design

Waymark is a phone-first web app for keeping a personal car maintenance log. It holds each car's spec sheet, a searchable repair log, and a home screen showing which services are due. It runs on Next.js on Vercel with a Neon Postgres database, the same setup as Provender (`ColeML/provender`). There is one user in v1. The data model is shaped so that family accounts can be added later without migrating data.

## Intent

The user does their own maintenance and looks things up at the parts counter or in the garage. Three questions come up most and should each take seconds to answer:

1. What does this car take? Oil type and capacity, filter part numbers, wiper sizes, VIN.
2. When did I last do X, and at what mileage?
3. What's due next, and at what mileage or date?

Mileage is typed in by hand. OBD-II sync is out of scope because the user doesn't connect a reader often enough for it to help.

## Goals and non-goals

- Goals: the three answers above for 2+ cars, with service intervals set per car (oil every 3,000 mi on one car, 5,000 mi on the other).
- Non-goals for v1: photo or receipt uploads, reminders by push or email, offline editing, cost reports, CSV export, sign-up, OBD-II.
- Anti-goal: logging an entry or an odometer reading takes more than a few taps on a phone. If it's slow, the due-soon view goes stale and the app stops being useful.

## Approaches

| Option | Outcome | Reason |
|---|---|---|
| Copy Provender's stack, replace Auth.js with self-hosted Better Auth, use Server Actions with no HTTP API | **Chosen** | Same deploy, tooling, and test setup as Provender. Better Auth is where new Auth.js-family work goes, and its tables live in the app's own database. |
| Keep Auth.js v5 like Provender | Rejected | Still beta (Provender pins `5.0.0-beta.32`). The Better Auth team has maintained it since September 2025 and points new projects to Better Auth. |
| Neon Auth (managed Better Auth) | Rejected | Adds a dependency on Neon's auth service and its pinned Better Auth version, for one account. |
| TanStack Start | Rejected | No benefit on Vercel for this app, and it diverges from Provender's patterns. |
| Hono API + tRPC like Provender | Rejected | Provender's API exists for an AI agent. Waymark has only the phone UI, so Server Actions are enough. Add an API if an agent ever logs entries. |
| Native app or offline-first local database | Rejected | Family access later needs a server anyway. An installable Progressive Web App (PWA) covers phone use. |

## Stack

Copy from Provender `origin/main`: Next.js 16 (App Router, React Compiler), React 19, TypeScript 7, Drizzle ORM 0.45 with `@neondatabase/serverless`, Tailwind 4, Base UI, lucide-react, zod 4, oxlint and oxfmt, Vitest with PGlite for database tests, Playwright for end-to-end tests, pnpm, Node 24.

Also copy these from Provender:

- `DATABASE_URL` (pooled) for runtime and `DATABASE_URL_UNPOOLED` for migrations. Locally, use a Neon branch or Provender's docker-compose and WebSocket proxy setup.
- The GitHub Actions workflow: lint, fmt check, typecheck, tests, build, then a `migrate` job on `main` that runs one at a time. Migrations never run in the Vercel build.

Added: `better-auth` with its Drizzle adapter.

## Auth and tenancy

- Better Auth with email and password. Sign-up is disabled. `scripts/create-user.ts` creates the single account and its garage membership.
- A **garage** owns the vehicles. Users belong to a garage through `garage_member`. Every vehicle row carries `garage_id`.
- `garageForSession(session)` returns the one garage in v1, the same pattern as Provender's `householdForSession`. Every query filters by the resolved garage, so adding a second user is just a new member row.

## Data model

All tables have `id` (uuid) and `created_at`. Money is stored in integer cents and miles as integers.

| Table | Columns |
|---|---|
| `garage` | `name`, `time_zone` (default `America/Chicago`), `due_soon_miles` (default 500), `due_soon_days` (default 30) |
| `garage_member` | `garage_id`, `user_id`, `role` (`owner` in v1) |
| Better Auth tables | `user`, `session`, `account`, `verification`, generated by Better Auth |
| `vehicle` | `garage_id`, `nickname`, `year`, `make`, `model`, `trim`, `vin`, `engine`, `oil_viscosity`, `oil_capacity_qt` (numeric), `archived_at` |
| `vehicle_spec` | `vehicle_id`, `category`, `label`, `value`, `part_number`, `notes`, `sort_order` |
| `service` | `vehicle_id`, `name`, `interval_miles`, `interval_months`, `archived_at`. At least one interval is required. |
| `log_entry` | `vehicle_id`, `performed_on` (date), `odometer` (nullable), `title`, `performed_by` (`DIY` or a shop name), `cost_cents`, `notes` |
| `log_entry_service` | `log_entry_id`, `service_id` |
| `log_entry_part` | `log_entry_id`, `part_number`, `description`, `quantity`, `cost_cents` |
| `odometer_reading` | `vehicle_id`, `read_on` (date), `miles`, `log_entry_id` (set when the reading came from a log entry) |

`vehicle_spec.category` is free text. The form suggests Fluids, Filters, Wipers, Tires, Electrical, and Other. A new car is created with suggested empty spec rows: oil filter, engine air filter, cabin air filter, driver wiper, passenger wiper, rear wiper, tire size, tire pressure, battery group, spark plugs.

A new car also gets suggested services, which the user can edit or delete. The intervals below are my calls.

| Service | Miles | Months |
|---|---|---|
| Oil change | 5,000 | 6 |
| Tire rotation | 5,000 | — |
| Engine air filter | 15,000 | — |
| Cabin air filter | 15,000 | 12 |
| Wiper blades | — | 12 |
| Tires | 50,000 | 72 |

The odometer on a log entry is optional. The form defaults it to the latest reading. When a log entry has an odometer value, saving it writes an `odometer_reading` linked to the entry in the same transaction. Editing the entry's odometer or date updates that reading, clearing the odometer deletes it, and deleting the entry deletes it.

## Due calculation

A pure function, unit-tested without a database. For each active service on a car:

- `last`: the most recent log entry tagged with that service, ordered by `performed_on`, then `odometer`.
- `current_miles`: the highest `miles` among the car's readings on the latest `read_on` date.
- For the mileage side, the most recent tagged entry that has an odometer value is used. If no tagged entry has one, the mileage side is No record.
- `due_miles = last.odometer + interval_miles`. `due_date = last.performed_on + interval_months`.
- Status:
  - **Overdue** when `current_miles >= due_miles` or today is on or after `due_date`.
  - **Due soon** when it is within `due_soon_miles` or `due_soon_days`.
  - **OK** otherwise.
  - **No record** when the service has never been logged. The card offers "log last time you did this" so the user can record a baseline.
- When both intervals are set, each side gets its own status, and the service takes the more urgent one. The card shows the side that set it, or mileage on a tie. (Builder's call, made during design review.)
- "Today" is the current date in `garage.time_zone`, an IANA name such as `America/Chicago`. The same zone sets the default `performed_on` and `read_on`. Vercel servers run on UTC, so without this an evening entry gets tomorrow's date. (Builder's call, made during design review. The default zone is an assumption.)

A reading lower than the previous one, or more than 5,000 mi above it, gets a warning before it is saved but is not blocked. Typos happen, and so do replaced instrument clusters. The car screen lists past readings, and any of them can be edited or deleted. A reading linked to a log entry is edited through that entry.

## Screens

Every screen requires a session. Text inputs use 16px text so iOS doesn't zoom, mileage fields use a numeric keypad, and tap targets are at least 44px.

| Route | Content |
|---|---|
| `/` | Due-soon home: one card per car with current mileage, services sorted overdue → due soon → no record → OK, and an "Update odometer" button that opens a sheet |
| `/cars/[id]` | Spec sheet: fixed fields at the top, spec rows grouped by category. Tapping a part number copies it. Editable in place. A list of odometer readings below, each editable or deletable. |
| `/cars/[id]/services` | The car's tracked services and their intervals |
| `/log` | Log list with search (case-insensitive match on title, notes, service names, part numbers, and part descriptions) and filters by car and service. Newest first. |
| `/log/new`, `/log/[id]` | Add or edit an entry. Opening `/log/new` from a service on the home screen pre-fills the car and service tag. |
| `/cars/new`, `/settings` | Add a car. Settings holds the due-soon thresholds and archived cars. |
| `/login` | Email and password |

The app ships a web manifest and icons so it installs to the home screen. The user is designing the icon. It needs no service worker beyond what installation requires.

## Builder's calls

- Whether search runs on each keystroke (debounced) or on submit.
- Seed data for local development.
